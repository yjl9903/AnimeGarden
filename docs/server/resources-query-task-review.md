# Resources Query Task 设计预期与现状核对

初次核对：2026-03-22；最近核对：2026-10-02。以下现状以当前代码为准。

## 背景

`resources` 查询模块面对的是复杂筛选 + 分页的场景。完整筛选条件很多，直接对完整查询做缓存时，命中率往往不高；但真实业务中，用户通常会先通过一个主关键词、标题匹配、subject、类型或字幕组等条件筛出一批有限结果，然后再继续细化筛选。

基于这个特点，模块引入了 `Task` 类和预取机制，希望把查询拆成两层：

1. 先用一组更粗的关键条件查询数据库，得到可以复用的中间结果。
2. 把这批中间结果缓存到进程内存中。
3. 对同一个粗查询下的后续细化请求，优先走内存筛选，而不是再次直接打数据库。
4. 只有内存缓存不足以判断最终分页结果时，才继续向后预取更多数据。
5. 如果预取达到上限，但底层数据库里仍可能存在更多结果，则回退到完整条件的精确查询，保证结果正确性。

目标不是完全替代数据库查询，而是尽量提高“同一类查询上下文中的复用率”，从而降低复杂筛选分页场景下的数据库压力和响应时间。

## 设计预期

当前模块的设计预期可以总结为：

### 1. Task 需要抽取“粗查询”

`Task` 的 key 不应该等价于完整过滤条件，而应该只保留最有代表性的主筛选条件，例如：

- `search`
- `include`
- `subjects`
- `types`
- `fansubs` / `publishers`

这样后续更细的过滤可以复用同一个 `Task` 的中间结果。

### 2. Task 结果需要缓存到内存

一次 `Task` 预取得到的结果应当缓存在内存里，供：

- 同一个请求的后续分页使用
- 同一时间的并发请求复用
- 后续相同粗查询、但更细过滤不同的请求复用

### 3. 内存筛选需要承担“细化过滤”

完整过滤条件中的一部分需要在数据库阶段完成，另一部分则应在 `Task` 缓存结果上做内存筛选，以降低数据库重复执行复杂查询的概率。

### 4. 预取必须是按需的

预取不能因为来了一个请求就无条件反复往后拉更多页。只有在“当前缓存不足以筛选出目标页最终结果”时，才允许继续向后预取。

### 5. 预取必须有总上限

为了避免单个 `Task` 无限扩张，占用过多内存或不断把大批数据从数据库搬到内存中，预取需要有一个较大的总上限。达到上限后，如果数据库仍可能有更多数据，就回退到完整条件的精确查询。

### 6. Redis 缓存故障不能阻塞数据库查询

Task 预取和完整条件的精确查询都可以通过 Redis 复用数据库结果。Redis 访问应有明确的等待上限，故障时允许查询回到数据库；数据库结果就绪后，不应再等待缓存写入成功才能返回。

## 当前实现已达到的部分

当前实现已经满足以下几点：

### 1. 已存在粗查询到 Task 的分层

`findFromTask()` 会优先把完整查询压缩成更粗的 `Task` 选项，再用完整查询选项在内存中做细筛。

当前粗查询分组包括：

- `search`
- `include`
- `subjects`
- `types`
- `fansubs` / `publishers`
- 其余情况回退为完整过滤条件

### 2. Task 结果会缓存在进程内存中

`Task.resources` 会保存预取结果。后续请求若命中同一个 `Task`，可以复用这批中间结果，而不是重新从数据库取同一批粗结果。

### 3. 并发请求会复用同一轮预取

当前实现把“按游标预取”的进行中 Promise 缓存在 `Map<number, Promise<void>>` 里。多个请求同时命中同一 `Task`、同一游标时，会等待同一轮预取，而不是并发重复打数据库。

### 4. 预取是按需推进的

当前 `findFromTask()` 的流程已经变成：

1. 先尝试用当前缓存做内存筛选。
2. 如果当前缓存已经足够筛出目标页，则直接返回。
3. 只有当前缓存不足，并且 `Task` 仍允许继续预取时，才向后按游标继续预取。

这符合“只有在收到的数据不够筛选出最终结果时，才预取下一页”的预期。

### 5. 预取存在总上限，超限后会回退到精确查询

当前已经引入了总预取上限：

- `RESOURCES_TASK_PREFETCH_MAX_COUNT = 1000`

当某个 `Task` 的内存预取达到上限，但数据库中仍可能存在更多数据时，`Task` 会停止继续扩容，此时 `findFromTask()` 会退出 Task 路径，调用 `findFromAccurateQuery()` 按完整条件和分页查询。该路径仍可命中查询缓存，缓存未命中时才访问数据库。

### 6. 查询缓存有超时、故障冷却和后台回写

上述 Task 预取使用 `findFromRedis()`，精确查询使用 `findFromAccurateQuery()`。两者各自通过进程内 memo 复用结果，并共用 Redis 读写保护；本地 Task 或 memo 命中时不访问 Redis，Redis 未命中时才执行对应的数据库查询。

Redis 查询缓存的故障处理如下：

- 未配置 Redis 或连接未 ready 时，直接跳过 Redis。
- 每次缓存读写的等待上限为 500ms。超时或操作失败后，当前 `QueryManager` 在 30 秒内跳过查询缓存读写；冷却结束后，下一次需要访问 Redis 的查询会重新尝试。
- 数据库查询成功后，Redis 回写在后台执行，不阻塞列表返回。后台写入失败同样触发冷却，错误会被捕获。

Redis 结果缓存和两条查询路径的 memo TTL 均为 5 分钟。这里的 500ms 限制的是单次缓存操作的应用层等待，不是整个列表请求的超时，也不会取消已经发送的 Redis 命令；迟到的拒绝仍会被处理。

该保护仅覆盖 resources 列表查询缓存。通知、RPC 和详情缓存沿用各自的 Redis 行为；本地 Task 的数据新鲜度仍由通知更新与 Task 清理机制决定，不能由 Redis 缓存的 TTL 保证。

### 7. 当前行为已有测试覆盖

目前测试覆盖的关键行为包括：

- 并发请求与后续请求对 `Task` 预取结果的复用
- 达到总预取上限后的停止扩容行为
- 预取和精确查询路径的 Redis 命中、读写超时、故障冷却及恢复访问
- 数据库结果不等待 Redis 回写，以及超时后迟到的读写失败处理

### 8. HTTP 入口限制深分页

`/resources` 和 `/feed.xml` 会拒绝 `offset + limit > 10000` 的请求，避免深分页把慢查询压力直接打到数据库。

### 9. 过期与容量淘汰会释放 Task 持有的 intern 对象

Task GC 每小时检查一次，两小时未刷新的 Task 会从 Task Map 中移除，后续访问会创建新
Task。移除 Task 时只会删除仍指向该 Task 原对象的 intern 项，避免旧 Task 的清理误删其他
Task 已经写入的更新对象。Task GC 和每日字符串池清理即使单次执行失败，也会继续调度下一轮。

### 10. API 分页信息统一放在 pagination

`QueryManager.find()` 返回 `{ resources, pagination, filter }`，其中 `pagination` 包含
`page`、`pageSize` 和 `complete`。`/resources` 及其 provider、页码和尾斜杠别名直接保留
该结构，不再返回与 `pagination` 同级的兼容字段 `complete`。旧调用方需要改读
`result.pagination.complete`。

`/collection/:hash` 的 `results[]` 每项同样使用这一结构。收藏夹仍对每个保存的筛选条件
查询第 1 页、最多 1000 条资源，分别通过 `results[i].pagination.complete` 表示是否完整；
本次响应结构统一不新增收藏夹请求分页参数。

## 当前实现尚未完全达到预期的部分

虽然整体机制已经基本成型，但若以“优化复杂筛选分页查询，并最大化细化查询的复用率”为目标，当前实现仍有几个关键偏差。

### 1. Task key 仍然偏细，缓存复用率还不够高

当前实现中：

- `search` task 仍然带上了 `exclude`
- `include` task 仍然带上了 `keywords` 和 `exclude`

这意味着一些本应共享同一个粗查询结果的请求，会被拆成多个不同 `Task`，从而降低中间结果复用率。

如果设计目标是“先按主关键词/主条件打粗缓存，再在内存里做细化过滤”，那么这部分还可以继续收敛。

### 2. 内存筛选语义与数据库筛选语义不完全一致

数据库层在 `include / keywords / exclude` 上使用的是 `titleAlt` 的 `ILIKE` 匹配；但当前内存筛选使用的是 `normalizeTitle(r.title).toLowerCase()`。

这带来一个问题：

- task 路径下的内存筛选结果
- 直接 fallback 到数据库时的 SQL 结果

二者理论上可能不完全一致。

这会削弱整个优化方案的可靠性，因为 `Task` 机制的前提之一就是“内存细筛应尽量等价于数据库细筛”。

### 3. Task 降级恢复仍依赖统一 GC 周期

某个完整查询及分页组合走过 fallback 后，会加入 `downgrade`，后续相同请求跳过 Task，改走精确查询路径。`clearDeadTasks()` 每小时清空该集合，因此这不是永久降级，但恢复时机仍依赖统一 GC 周期，而非该查询自身的状态。

可以进一步为降级记录设置独立过期时间，让暂时无法利用 Task 的查询更及时地重试。这与 Redis 故障后的 30 秒冷却是两套独立机制。

### 4. Task 数据新鲜度仍依赖变更通知

cron 与 server 之间通过 Redis 通知更新本地 Task。当前请求读取 Task 时没有独立的过期校验，通知缺失时主要依靠每小时执行的 GC 淘汰两小时未刷新的 Task；重连后也没有主动补齐漏掉的变更。

查询缓存的短超时和后台回写解决了 Redis 读写阻塞响应的问题，但没有解决通知中断时的旧数据问题。后续仍需为 Task 增加请求时的过期检查，并在重连后失效缓存或校验数据库版本。

## 结论

以当前实现来看，这个模块已经基本具备了原始设计思路的主体结构：

- 有 `Task` 这一层来承载中间结果
- 有内存缓存
- 有并发复用
- 有按需向后预取
- 有总预取上限
- 有超限回退到精确查询的保护逻辑
- 有 Redis 查询缓存的短超时、故障冷却和后台回写

因此，从“模块机制是否已经落地”这个角度看，答案是：**基本达到预期**。

但如果从“是否已经充分实现最初设计目标，即显著优化复杂筛选分页场景，并稳定提升细化筛选的复用率”来看，答案是：**部分达到，仍未完全达到**。

当前最主要的剩余问题不是预取框架本身，而是：

1. `Task` 粗查询的粒度仍可继续收敛。
2. 内存筛选与数据库筛选的语义还需要对齐。
3. Task 降级后的恢复时机仍可细化。
4. 通知中断后的 Task 数据新鲜度缺少主动校验。

## 后续建议

后续改进应围绕上述剩余问题展开：

### 1. 继续收敛 Task key

目标：让同一主查询上下文下的更多细化请求可以命中同一个 `Task`。

### 2. 对齐内存筛选与 DB 筛选语义

目标：保证 task 路径和 fallback 路径在结果上尽量一致，避免“缓存优化改变结果语义”。

### 3. 为 Task 降级记录设置独立过期时间

目标：让查询按自身的降级时间重新尝试 Task，减少对每小时统一 GC 的依赖。

### 4. 补齐通知中断时的数据新鲜度保护

目标：通过请求时的 Task 过期校验和重连后的缓存失效或版本核对，让 Redis 通知中断后的旧数据有明确的刷新边界。
